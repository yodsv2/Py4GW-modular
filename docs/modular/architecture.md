# Native Modular BottingTree Recipes

Modular recipes now live as native Python `BehaviorTree` functions under `Sources/modular_recipes`.

Runtime path:

```text
Sources/modular_recipes grouped Python modules
  -> module-local RECIPES metadata
  -> Sources.modular_recipes.catalog discovers module:function
  -> BottingTree.SetCurrentNamedPlannerSteps
  -> recipe function returns BehaviorTree
```

`BottingTree` remains the runtime owner for ticking, blackboard state, pause/resume/stop, loop handling, HeroAI integration, movement pause flags, services, party setup, and recovery. Recipe modules only build trees.

## Recipe Layout

Recipes are grouped by kind, campaign, and area/topic. For example:

```text
Sources/modular_recipes/
  missions/
    prophecies/
      ascalon.py
      kryta.py
      maguuma_jungle.py
    nightfall/
      istan.py
      kourna.py
  quests/
    factions/
      story.py
  routes/
    prophecies/
      transit.py
```

Each recipe is a plain function returning `BehaviorTree`, in the style of `Factions Leveler Redux.py`:

```python
def fort_ranik() -> BehaviorTree:
    return BT.Sequence(
        name=FORT_RANIK_TITLE,
        children=[
            BT.LeaveParty(),
            BT.Travel(target_map_id=29),
            BT.LoadParty(max_heroes=4),
            BT.EnterChallenge(target_map_id=29),
            BT.MoveAndKill(...),
        ],
    )
```

Grouped modules expose plain `RECIPES` metadata and optional route preview points. They do not expose executable step dictionaries, per-step metadata, or recipe-local planner-step builders.

## Catalog Surface

Use `Sources.modular_recipes.catalog` for discovery and prebuilt assembly:

- `all_specs`
- `get_spec`
- `get_recipe_module`
- `get_recipe_factory`
- `planner_steps_for_specs`
- `recipe_route_points`
- `specs_from_rows`
- `derive_region_spans`

`RecipeSpec` points at `module:function`. `planner_steps_for_specs` converts a sequence of specs into named BottingTree planner phases, where each phase is one whole recipe function.

Prebuilt campaign ordering lives in `Sources/modular_recipes/prebuilt`.

## Recording and Targets

Use `Widgets/Automation/modular/Modular Recorder.py` to capture new native Python recipe snippets. It records concise `BT.*` calls, route preview points, and target-registry appendix entries.

NPC, enemy, and gadget targets must use encrypted names from `PyAgent.PyAgent.GetAgentEncName`. Display names are metadata only and must not be used as a runtime matching fallback. The collection queue lives in `docs/modular/target_collection_queue.md` and is generated by:

```powershell
python Sources/modular_recipes/tools/audit_targets.py
```

`Widgets/Automation/modular/Verified Modular Blocks.py` uses the same target audit as the CLI so in-client verification and offline validation report the same blockers.

## Validation

Use focused checks:

```powershell
python -m py_compile <changed python files>
python Sources/modular_recipes/tools/test_python_recipe_compile_shape.py
python Sources/modular_recipes/tools/test_modular_recipe_registry.py
python Sources/modular_recipes/tools/test_modular_botting_tree_adapter.py
python Sources/modular_recipes/tools/test_modular_target_audit.py
python Sources/modular_recipes/tools/test_modular_recorder_emitters.py
python Sources/modular_recipes/tools/validate_modular_architecture.py
```

The removed JSON compiler path must not be reintroduced. `Py4GWCoreLib.modular` remains only as a small support namespace for non-recipe helpers such as MerchantRules selectors and named target definitions.

`validate_modular_architecture.py` passes when the native Python recipe structure is healthy and prints target-collection warnings when encrypted-name/model-id data or nearest-target replacements are still missing. Use strict mode when you explicitly want that target audit debt to fail the command:

```powershell
python Sources/modular_recipes/tools/validate_modular_architecture.py --strict-targets
```
